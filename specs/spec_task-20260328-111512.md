# Tennis Zeitparser — Technische Spezifikation

## 1. Projektübersicht

Das Modul **Tennis Zeitparser** ist ein reiner Backend-Eingabe-Parser, der natürlichsprachliche Datums- und Zeitangaben (Deutsch und Englisch, inkl. Tippfehler) in ein strukturiertes `TimeWindow`-JSON-Objekt umwandelt. Es handelt sich um **keinen eigenständigen Screen**, sondern um eine wiederverwendbare API-Komponente, die in die bestehende Tennis Booking App unter `/opt/Tennis_Booking/` integriert wird. Der Parser wird per `POST /api/parse-time` angesprochen und liefert ein normiertes Zeitfenster zurück.

---

## 2. Zielgruppe & User Stories

- Als **Entwickler der Tennis Booking App** möchte ich die Freitexteingabe des Users an einen Endpoint schicken, damit ich ein strukturiertes Zeitfenster zurückbekomme, ohne selbst Parsing-Logik implementieren zu müssen.
- Als **Endnutzer der Booking App** möchte ich „morgen früh" oder „next Sunday afternoon" eintippen können, damit ich keine exakten Uhrzeiten manuell auswählen muss.
- Als **QA-Entwickler** möchte ich den Parser isoliert testen können, damit ich sicherstellen kann, dass alle Grenzfälle korrekt interpretiert werden.

---

## 3. Features & Screens

> **Hinweis:** Dieses Modul hat keine eigenen Screens. Es stellt ausschließlich einen API-Endpoint bereit.

### 3.1 `POST /api/parse-time` — Kernfunktion

- Nimmt einen Freitext-String entgegen
- Erkennt relative Datumsbegriffe (DE + EN)
- Erkennt Tageszeit-Fenster (DE + EN)
- Korrigiert Tippfehler (bis 2 Zeichen Abweichung via Levenshtein)
- Gibt ein `TimeWindow`-Objekt als JSON zurück
- Gibt einen `confidence`-Wert und den **interpretierten Begriff** zurück (für optionales UI-Feedback)

### 3.2 `GET /api/parse-time/health` — Health Check

- Einfacher Statuscheck: `{ "status": "ok" }`
- Für Monitoring und Deployment-Verifikation

## 5. Technische Architektur

### Frontend
- **Keines** — der Parser ist ein reines Backend-Modul.
- Integration erfolgt durch die bestehende Tennis Booking App (beliebiges Frontend), die den Endpoint per HTTP aufruft.

### Backend
- **Sprache:** Python 3.x
- **Framework:** Flask (Micro-Endpoint, ergänzt die bestehende App oder läuft als Sidecar-Service)
- **Kernmodul:** `time_parser.py` (regelbasiert, kein ML)

### Abhängigkeiten (`requirements.txt`)
```
flask>=2.0
python-dateutil>=2.8
```
> Levenshtein-Distanz wird als einfache Hilfsfunktion selbst implementiert (keine externe Lib nötig).

### API-Schnittstellendefinition

**Request:**
```http
POST /api/parse-time
Content-Type: application/json

{
  "query": "morgrn zwischen 10:00 und 13:00"
}
```

**Response (Success):**
```json
{
  "date": "2025-01-29",
  "from": "10:00",
  "to": "13:00",
  "interpreted_as": "morgen 10:00–13:00",
  "confidence": 0.92,
  "multi_day": false
}
```

**Response (Wochenende — multi_day):**
```json
{
  "dates": ["2025-02-01", "2025-02-02"],
  "from": "09:00",
  "to": "21:00",
  "interpreted_as": "dieses Wochenende",
  "confidence": 1.0,
  "multi_day": true
}
```

**Response (nicht erkennbar):**
```json
{
  "date": null,
  "from": null,
  "to": null,
  "interpreted_as": null,
  "confidence": 0.0,
  "multi_day": false,
  "error": "Zeitangabe konnte nicht interpretiert werden."
}
```

## 6. Deployment

- **Installationspfad:** `/opt/Tennis_Booking/time_parser/`
- **Integration:** Der Flask Blueprint wird in die bestehende Tennis Booking App registriert:
  ```python
  from time_parser.parse_time_route import time_parser_bp
  app.register_blueprint(time_parser_bp)
  ```
- **PM2 Prozessname:** `tennis-booking` (bestehender Prozess — kein neuer Prozess nötig, da Blueprint-Integration)
- **Kein separater Apache Proxy Pfad** erforderlich — der Endpoint `/api/parse-time` läuft unter der bestehenden App-Domain
- **Alternativ als Sidecar** (falls separate Prozesse gewünscht): PM2-Prozessname `tennis-zeitparser`, Port `5001`, Apache ProxyPass `/api/parse-time → localhost:5001`
